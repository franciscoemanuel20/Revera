# Fundação da Reverá — 25/08/2026

Registro do que foi decidido *antes* deste scaffold (não por quem escreveu o
código) e do que ficou como escolha técnica dentro do escopo permitido, para
quem chegar depois não precisar reconstruir o raciocínio.

## O que já veio decidido (não é escolha deste scaffold)

- **Schema completo** (`supabase/migrations/00000000000001_init.sql`) — as
  29 tabelas, os enums de status e as policies de RLS foram desenhados
  antes; a implementação seguiu o SQL à risca, sem alterar coluna, tipo ou
  constraint nenhuma.
- **Paleta e tipografia** (`src/styles/tokens.css`) — cores, fontes
  (Fraunces/Manrope) e a proibição de Inter/Space Grotesk/roxo-azul vieram
  prontas na missão. O que este scaffold decidiu foi *como* implementar
  isso em Tailwind (ver abaixo).
- **Conteúdo de `seeds/`** — códigos de cor, níveis de grisalho e as 15
  perguntas de FAQ são dados reais da marca, não inventados aqui.

## Decisões técnicas tomadas dentro do escopo

- **Opacidade de cor via `rgb(var(--x-rgb) / <alpha-value>)`, não
  `var(--x)` puro.** Os componentes usam bastante `text-ink/60`,
  `bg-ink/40` etc. Um valor de cor Tailwind que é só uma CSS var
  (`var(--ink)`) não aceita modificador de opacidade de forma confiável
  entre versões — o build não vê os canais RGB dentro da var. Por isso
  `tokens.css` define `--ink-rgb: 27 23 18` (e equivalentes) além do
  `--ink: #1b1712` original, e `tailwind.config.ts` usa o formato com
  `<alpha-value>`. Ver comentário em `src/styles/tokens.css`.
- **Pagamento e frete como interface + mock**, escolha de provider por
  presença de env (`PAYMENT_PROVIDER` para pagamento;
  presença de `SUPERFRETE_TOKEN` para frete) — mesmo princípio de
  "credencial ausente → adapter demo" que o projeto irmão
  (`saas-metodo-francisco/src/lib/providers/index.ts`) já usa. Nenhum dos
  dois adapters reais existe; os branches `infinitepay`/`superfrete`
  lançam erro de propósito.
- **`seeds/products.json` com `price_cents: null`** — a coluna
  `product_variants.price_cents` é `NOT NULL` no banco, então a variante
  seed nasce `is_active: false` e o produto `status: 'draft'`.
  `scripts/seed.mjs` recusa (com aviso, não erro fatal) tentar upsertar uma
  variante sem preço, em vez de violar a constraint silenciosamente.
- **FAQ com resposta desconhecida nasce `is_visible: false`** — o texto
  literal `"TODO: aguardando definição"` não pode aparecer para um cliente
  de verdade só porque ninguém filtrou antes de publicar.

## Verificação real (pós-scaffold, mesmo dia)

O agente que gerou o scaffold não tinha rede/Node disponível e só validou
sintaxe estaticamente. Instalei Node 20 via nvm e rodei a validação de
verdade — e ela pegou dois problemas reais:

1. **`next@14.2.15` tinha CVE conhecido** (`npm audit`: alta severidade,
   corrigido só a partir de `15.5.16`+; não existe backport de segurança na
   linha 14.x apesar de existir um `14.2.35`). Como este é projeto novo, sem
   código legado para quebrar, subi direto para **`next@15.5.24`** (tag
   `backport` do pacote — versão de manutenção da 15.x, sem exigir React 19:
   o peer dependency aceita `^18.2.0`, então `react@18.3.1` ficou como
   estava). Vulnerabilidades restantes (`npm audit`) são todas em
   ferramental de dev (`vitest`/`esbuild`/`vite`) — não vão para o bundle de
   produção; fica registrado como débito conhecido, não bloqueante.
2. **Next 15 tornou `cookies()` assíncrono** em Server Components —
   `src/lib/supabase/server.ts` usava `cookies()` de forma síncrona.
   Corrigido (`createClient` agora é `async`, `await cookies()`), e o tipo
   de `setAll` (`TS7006`, implícito `any`) foi anotado explicitamente com
   `CookieOptions` do `@supabase/ssr`. Nenhum outro arquivo ainda importa
   esse client, então o raio de impacto era só este arquivo.

Depois da correção: `npm install`, `npm run typecheck`, `npm run test`
(6/6) e `npm run build` (produção) rodaram de verdade e passaram. Também
rodei `scripts/verify-no-secrets-in-bundle.mjs` contra o build e um grep
manual por `12981409901` em `.next/` — nenhuma ocorrência, como esperado
nesta fase (o número ainda não foi implementado em lugar nenhum).

`package-lock.json` foi commitado (não existia; sem ele, instalações
futuras não são reprodutíveis).
